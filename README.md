## Run locally (Windows PowerShell)

```powershell
git pull origin main
Copy-Item .env.example .env
npm install
npm run dev
```

Open the localhost URL printed by Vite (normally http://localhost:5173).

`.env.example` holds a browser-safe **publishable** Supabase key for this isolated project. `.env` is ignored by Git. Never commit a Supabase service_role key, secret key, or database password.

## What's set up

- React + TypeScript + Vite, React Router, Tailwind CSS v4, TanStack Query
- Supabase Auth with customer and store_owner roles
- Seven public database tables with Row Level Security enabled
- 16 sample medicines
- Private `prescriptions` storage bucket (5MB; JPG, PNG, PDF)
- PostgreSQL order creation and status-change functions, including inventory locks and stock restoration
- Automated expiry of unanswered orders using pg_cron, one-minute schedule
- Self-service store setup on the store-owner dashboard

## Start using the app

1. Start the dev server and register as **store_owner** with a valid email. Confirm your email if Supabase requires it.
2. Open **Store orders**. Enter a pharmacy name, full address, delivery pincodes and allow browser geolocation to create the store.
3. The new store gets initial **demo** inventory for all medicines. Review/edit stock and prices in **Inventory**.
4. In another browser window, register as **customer**, select medicines and use pickup location or a matching delivery pincode.
5. Select the pharmacy, place an order and check status changes in **My orders**.
6. Create up to four independent store-owner accounts if you want the four-store demo. Run the demo account seeder below to create demonstration login credentials.

For pickup of prescription-required medicines, the customer brings the prescription to the store. Delivery requires a file upload.

## Database reproducibility

The SQL source is in `supabase/migrations/`. It is **already applied** to the new project. These files are for reproducibility, not instructions to push duplicate migrations to this configured project.

For another *empty* Supabase project only, install Supabase CLI, link to the *new target project*, and run `npx supabase db push` after reviewing the migrations and ensuring they are not already present. The configured project already has applied migrations via the connected API and may have migration-history differences from local CLI files.


## Create five demo accounts and four demo pharmacies

The database is already initialized, but Supabase Auth demo users require **server-side Auth Admin provisioning**. The script at `scripts/seed-demo-accounts.mjs` creates **1 customer and 4 store owners**, four Shirpur-area pharmacy records, and partial/demo inventory, all in the isolated `kkkolpwdxzgscpbagmfk` project. It does **not** touch older projects.

In Windows PowerShell, after `git pull origin main` and `npm install`, open **only the new project's** [API Keys page](https://supabase.com/dashboard/project/kkkolpwdxzgscpbagmfk/settings/api-keys). Copy the **service_role** key (or compatible secret key) but do **not** paste it into chat or commit it. Enter the key through a secure local prompt:

```powershell
$secure = Read-Host "Paste the NEW project's service_role key" -AsSecureString
$ptr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure)
try { $env:SUPABASE_SERVICE_ROLE_KEY = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($ptr) }
finally { [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($ptr) }
node scripts/seed-demo-accounts.mjs
Remove-Item Env:SUPABASE_SERVICE_ROLE_KEY
```

**Never use a key from another Supabase project.** The seeder hardcodes and validates the new project's URL, generates strong passwords, and writes them to a **gitignored local** file named `demo-credentials.local.json`. It does not print passwords into chat or GitHub. Keep this file private; do not upload it. If a demo email already exists, the script skips that user without resetting their password. Run it once, and don't delete the credential file unless you have safely saved the new passwords.

Expected account emails (passwords are randomly generated by the script):
- `demo.customer@example.com` — customer
- `demo.pharmacy1@example.com` — Shirpur Central Pharmacy
- `demo.pharmacy2@example.com` — Shirpur Care Pharmacy
- `demo.pharmacy3@example.com` — Eastside Medical Store
- `demo.pharmacy4@example.com` — Shirpur Health Point

These are fictional demonstration identities and locations, not real verified pharmacies. Treat all inventory and prices as sample data. After running the seeder, check Supabase Authentication → Users, and sign in with an account from your local credentials file.
